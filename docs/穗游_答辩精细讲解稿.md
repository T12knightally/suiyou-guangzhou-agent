## 1. 选题思路：为什么做大学生周末出行

### 可直接口述

“我从一个很具体的场景出发：两名学生周六从学校去市区，每人不超过150元，希望轻松一些，晚上八点前回来。这句话看起来简单，实际同时涉及预算、距离、体力、天气、营业时间和返程。学生通常要在攻略、地图、天气和场馆官网之间反复切换，再自己拼成行程。因此，我把项目目标定为把这些分散信息组织成可核算的行动计划。”

“选择广州，是为了让最小版本的范围可控。广州有大学城、五山等不同高校出发地，也有博物馆、图书馆、公园和历史街区，能覆盖文化、休闲、雨天室内等典型需求。首版准备20个种子地点，出发地可以自由填写，不绑定某一个校区。”

### 从场景推导需求

| 用户原话 | 工程含义 | 验收方法 |
| --- | --- | --- |
| 每人不超过150元 | 区分人均与总额，算入往返交通 | 独立复算门票、车费、餐饮、预留 |
| 两个人从学校出发 | 人数明确，校区地址能定位 | 高德定位实际出发地，计算同行总额 |
| 不想太累 | 将模糊偏好转成可检查指标 | 轻松节奏步行估算不超过90分钟 |
| 晚上八点前回来 | 限制回到出发地的时刻 | 必须包含完整返程，而非最后一站结束 |
| 下雨怎么办 | 天气会改变候选集 | 优先室内；严重天气暂停 |

这些是从任务场景推导的需求假设，没有做过学生访谈或满意度调查，因此不能说“调研发现某比例学生需要”。可以说这个场景具体、约束明确，适合展示多工具协作，下一步再通过真实用户测试验证需求优先级。

### 选题价值与取舍

本项目的展示价值在于：工具观察能改变后续行动，例如下雨后筛选室内、闭馆后换点、路线失败后比较其他组合。难点也正来自这些依赖关系。为控制范围，首版只做广州同日出行、最多两站；不做跨城酒店安排，不自动订票或支付，不声称全城最优。

### 可以这样解释自己的工作方法

“我先把能否通过验收的条件写清楚，再把接口和计算分开。这样外部服务不稳定时，仍能在离线场景中检验预算和时间逻辑；真实配置可用后，再检验数据接入和模型选择。每次发现错误，保留失败记录，增加针对性的测试，并同步报告中的能力描述。”

顺序很重要：先明确硬约束，再设计工具边界，最后接界面。否则容易做出好看的旅游推荐页，却无法回答‘车费怎么算’、‘是否包括返程’和‘闭馆时怎么办’。

## 3. 系统架构：模型负责什么，程序负责什么

### 可直接口述

“架构上，我把自然语言理解、工具决策、事实查询和约束计算分开。模型负责理解用户表达，并根据观察选择工具和候选地点；程序负责检查参数、读取真实接口结果、计算费用和时间。模型说某个行程可行，并不等于系统会接受，必须经过build_plan的硬约束校验。”

流程：用户表单/文本 → 需求提取与原文核对 → 合法结构化条件 → 模型工具循环 → 天气/地点查询 → build_plan路线与约束求解 → 行程或失败说明 → JSON归档、网页、TXT与打印。

| 文件或目录 | 职责 | 答辩时可解释的重点 |
| --- | --- | --- |
| app.py | HTTP入口与会话状态 | 请求如何进入Agent，何时更新会话 |
| agent/requirements.py | 自然语言字段提取及证据核对 | 模型提取值如何与用户原话一致 |
| agent/core.py | 工具循环、状态、组合求解、核算和保存 | 为什么不让模型自己决定预算通过 |
| agent/providers.py | 演示/在线数据适配 | 高德和天气接口的异常如何处理 |
| agent/venue_facts.py | 官方资料应用 | 资料适用时间、来源和降级规则 |
| config/venue_facts.json | 官方事实、URL、核验日期 | 可追溯事实和未知值的区别 |
| prompts/system.md、web/ | 模型行为说明、消费者界面 | Prompt不是唯一防线，网页不是调试日志 |

### 为什么不用更复杂的框架

业务服务使用Python标准库与原生HTML/CSS/JavaScript，启动和审阅成本低。当前规模下，不需要为了框架数量而引入向量库或多智能体。没有RAG检索链，没有自主联网爬遍所有网站，也没有长期用户画像。官方资料是有限、可审计的结构化知识。

### 为什么仍然是Agent

当前实现是受限的工具调用Agent：模型看到上一步工具结果后，选择下一步工具和候选；首次建案失败时有第二次重选机会。动作空间和执行边界由程序控制。它不是无限自主通用Agent，也没有宣称多智能体协作。

## 4. 需求追问与记忆：从一句话到可靠字段

### 具体任务

用户必须给出出发地、日期、人数、每人预算、出发时间、最晚返回时间。兴趣、步行节奏、必去/排除地点、室内偏好和站数可以增量修改。支持1至12人、人均预算1至2000元、同日且至少2小时的可用时间。

有自然语言消息时，先调用extract_trip_requirements。提取结果必须带每个字段对应的用户原文，程序再核对引用、数字、时间、日期和地点。模糊的“两人150元”不能直接当作每人150元；需要确定这是人均还是总预算。

### 真实三轮案例

| 轮次 | 用户输入 | 处理结果 |
| --- | --- | --- |
| 1 | 周六两个人从广州大学大学城校区出发，每人150元，想轻松一点 | 缺少起止时间，返回needs_input，保留已接受字段 |
| 2 | 早上九点出发，晚上八点前回来，必须去广东省博物馆和广州图书馆 | 沿用第一轮条件，补时间及必去；生成省博＋广图 |
| 3 | 每人改成80元，不去广东省博物馆，只逛一个地方 | 更新预算，排除省博，限制一站；保留广图要求 |

### 真正遇到的困难

如果每轮重新提交表单默认值，旧默认值可能覆盖用户刚说的新偏好；如果保存旧message，下一轮又会重复提取旧要求；如果先保存再校验，负预算等非法输入会污染后续状态。

解决方法是把会话视作“已接受结构化条件”，新消息仅增量更新，旧message不重放。提取和输入验证通过后才提交可接受状态；非法、拒绝和越界请求不覆盖之前合法条件。这样缺参时可以继续补充，非法修改也不会破坏前一份有效需求。

### 验证与局限

三轮案例经真实HTTP和模型运行保存，见evidence/repairs中的conversation_1_missing、conversation_2_complete、conversation_3_adjust。HTTP验证还检查“负预算被拒绝后，原150元预算仍保留”。记忆仅在本机进程内，重启丢失；历史行程JSON仍保留。它不是会记住个人长期兴趣的产品。

## 5. 工具协作：Function Calling实际怎样运行

### 用一个容易理解的比喻

模型像负责调度的规划员，工具像有明确输入输出的查询和计算岗位。工具调用不是让模型随便运行代码，而是让它在事先声明的函数中提交结构化参数。执行器检查工具名称和参数，再调用真实Python逻辑，返回观察给模型。

| 层级 | 工具/动作 | 实际作用 |
| --- | --- | --- |
| 需求阶段 | extract_trip_requirements | 从用户文本提取增量字段与引用证据 |
| 规划模型可调用 | query_weather | 查询天气，改变室内/室外选择 |
| 规划模型可调用 | query_places | 查询地点并合并适用官方资料，最多6候选 |
| 规划模型可调用 | build_plan | 提交1至3个不同候选ID，计算可行方案 |
| 程序内部子步骤 | query_route | 查询去程、馆间和返程，比较不同顺序 |
| 程序内部子步骤 | calculate_cost、check_schedule | 核算费用及时间、步行条件 |
| 程序内部子步骤 | save_itinerary | 保存输入、输出、状态、Trace和用量 |

注意：报告工具清单里的路线、核算、保存是工程动作；并不是全部直接暴露给规划模型。解释这个层级，才能准确回答“模型究竟决定了什么”。

### 控制循环的规则

先查询天气，再根据天气检索地点，再建案。工具结果以结构化观察进入下一轮。最多8次规划模型响应、12次外层工具调用，需求提取另最多1次；build_plan最多2次。一个build_plan会触发多个路线查询，因此外层工具数、路线事件数、HTTP重试次数不相等。

使用兼容Chat Completions tools/tool_calls的接口，当前配置模型标识为qwen3.8-flash；具体可用名称以提供商为准。Qwen已留下真实工具调用证据，DeepSeek为可选接入，不自动故障转移。本项目未进行系统性模型排名，不能声称选用模型最好或最便宜。

全任务120秒是尽力而为的时间预算，向网络请求传递剩余时间，并非独立进程强制终止。模型单请求45秒且不自动重试，数据请求6秒、最多重试一次。限制用于控制成本和等待，不是生产级高可用保证。

## 6. 规划算法：如何同时满足预算、时间与体力

### 候选选择与组合比较

20个种子用于发现地点；检索最多返回6个，模型提交1至3个候选。求解器比较同片区两站的两种顺序和单站，最多安排两站，并检查必去、排除、室内和站数条件。它采用有界组合搜索，不是全广州最优路径算法。

已通过约束的组合按以下规则评分：100×站数＋150×有适用官方开放依据的站数＋10×兴趣匹配数－0.1×交通分钟。分数体现当前设计偏好，不是通过用户调查学习出的模型。已知运营资料被优先考虑，但低分方案也可能满足用户需要。

### 费用怎么算

每人费用＝全部门票＋全部交通（含返程）＋35元餐饮饮水＋15元预留。同行总费用＝每人费用×人数。未知门票使用每点30元规划额度，未知交通使用每段10元额度，必须保留未知标记。这些是估算占位，不代表票价或实际消费上界。

### 时间与体力怎么检查

| 约束 | 检查方式 | 需要说明的局限 |
| --- | --- | --- |
| 开放时段 | 已知规则下，完整停留落在开放区间内 | 未知时段保持未知，不算已核实营业 |
| 最晚入场 | 到达时刻必须早于停止入场时间 | 16:00截止时，16:00到达不能接受 |
| 返程 | 加上回到出发地的路线，不能超过用户截止 | 路线是查询时估算，非未来班次保证 |
| 用餐与缓冲 | 第一站后安排45分钟用餐；公交15分钟、步行3分钟缓冲 | 固定规则尚未覆盖排队和特殊交通波动 |
| 步行负担 | 轻松90分钟、普通150分钟上限；每站计15分钟馆内估算 | 不等同实测步数，未建模坡度和个人体力 |

### 降雨与失败的调整

雨天优先室内；主方案已全室内则复用为雨天安排，避免重复查询同一方案。晴天另外尝试室内备选。严重天气暂停，不强行推荐出游。某段路线失败会使相关组合不可用；最终没有可行组合时，返回原因或需要修改的条件，不捏造一条路线填补。

## 7. 真实成功案例：逐步讲清一次请求

历史run_id：85fb96702ab84d8d。2026年10月14日查询10月17日行程；广州大学大学城校区出发、2人、每人150元、09:00至20:00、轻松节奏、必去省博和广图。

### 运行步骤与观察

1. 模型提取第二轮消息里的时间和必去地点，程序核对原文，合并第一轮条件。
2. 高德定位校区；规划模型首先调用天气，观察为降雨。
3. 模型请求室内地点；高德POI与适用官方资料共同返回候选。
4. 模型提交省博和广图；程序比较顺序、查往返与馆间路线。
5. 费用、开放、入场、返程和步行检查通过；主案全室内，复用为雨天安排。
6. 保存24个Trace事件，返回页面行程及下载/打印内容。

| 时间 | 行动 |
| --- | --- |
| 09:00-10:14 | 从学校乘公共交通前往省博 |
| 10:14-11:44 | 广东省博物馆参观 |
| 11:44-12:29 | 用餐与休息 |
| 12:29-12:37 | 步行到广州图书馆，含3分钟缓冲 |
| 12:37-13:37 | 广州图书馆参观 |
| 13:37-14:48 | 返回出发校区 |

门票0＋0，交通5＋0＋5，餐饮35，预留15，合计60元/人、120元/两人，人均预算余量90元。馆间实际道路345米、约5分钟，加3分钟缓冲。总步行估算79分钟，符合轻松上限。14:48返回只说明在用户最晚时间之前，不需要刻意安排到20:00。

模型响应4次：1次提取、3次规划。模型用量6869输入＋347输出＝7216 Token。任务保存前耗时约13.65秒，6个路线事件成功、0失败。路线事件超过行程中的3段，是因为求解器比较不同顺序；不能将其解释为用户要坐6段车。

免费范围限普通入馆/相关公共区域，省博预约名额未核验。结果可用于历史说明，不代表现在的天气、票价或可预约名额。

## 8. 调试复盘一：公交失败与未知票价

### 困难A：省博和广图很近，为什么做不出双站方案

现象：旧真实在线记录f29fe1974c634570中，共15个路线事件，9个失败。省博至广图一次没有公交路线，另外8次出现高德10021错误。程序当时偏重公交，短距离场馆也用公交查询，导致本来可以步行的组合被淘汰。

定位方法：检查真实query_route输入、输出及错误，区分“路线模式不合适”和“外部接口返回错误”。不能仅凭10021就断言配额、频率或平台故障根因已经确定。

修复方法：直线距离不超过1.5公里时优先请求高德真实步行接口。直线距离只用于选择路线模式，不作为最终道路距离；必须取得有效distance、duration等字段。步行失败再回退公交。限制模型至多提交3个候选，高德请求全局间隔至少0.45秒，减少不必要的调用。

验证：新版真实双站案例中6个路线事件全部成功，馆间取得345米、约5分钟的道路结果。这个对比发生在不同时间和请求条件，支持“实现能处理该例”，不能证明节流对所有接口错误有因果上的彻底修复。

### 困难B：免费场馆为什么还预留30元门票

现象：POI缺少可以直接采信的入场价格和日期营业规则，旧程序为省博按未知票价预留30元；旧单站估算90元/人。

修复方法：人工读取官方参观与预约页面，保存来源URL、原文、抓取时间和HTML哈希，把免费范围、周闭馆日、最晚入场和预约提醒作为结构化规则。设置7天核验有效期及明确的周历适用区间，过期不能当新事实。

验证：省博与广图常规免费范围内门票各0元，新双站方案估算60元/人。减少的是未知票价占位，并没有替用户预约成功。通过周闭馆及最晚入场边界测试，避免只有界面显示“免费”而求解器没采用规则。

### 可以归纳出的工程经验

“面对失败，我先看工具证据，再决定修改哪一层。路线问题需要改路线模式和调用策略，价格问题需要补可靠资料；增加一段‘请认真规划’的提示词不能替代这些修复。”

## 9. 调试复盘二：状态、重试与数据类型

| 实际问题 | 风险/原因 | 修复办法与证据 |
| --- | --- | --- |
| 非法修改污染会话 | 验证之前就写入状态，后续请求沿用错误值 | 仅提交接受的结构化字段；HTTP验证负预算后仍保留150元 |

| 过去日期错误优先级 | 未配置接口时先返回needs_configuration，掩盖日期非法 | 前置日期校验；失败日志和回归断言保留 |

### 为什么限制重试

如果允许模型无限重试，路线平台持续超时会带来长等待和额外Token成本。当前让模型有一次重选机会，同时限制规划响应、工具次数、建案次数及全任务时间。达到边界就明确结束，让用户调整条件或稍后重试。

### 答辩表达建议

不要只说“优化了性能和稳定性”。可以具体说：“发现缺失步行距离被当作0后，我把它改为显式异常，因为未知信息不能帮助一个方案通过硬约束。”这种解释能把代码改动与业务后果对应起来。

## 10. 数据治理：部分闭馆和入口变化怎么处理

### 当前资料覆盖的准确口径

20个种子中10处有官方来源。其中省博、广图、南越王宫、农讲所4处有运营规则；前三处有明确适用范围的入场价格，农讲所票价仍未知。陈家祠、粤剧艺术博物馆、沙面、永庆坊、荔湾湖公园、越秀公园6处只具介绍来源。其余10处仍是种子信息。

### 南越王宫：不是一句“关闭”就够了

官方2026年10月4日公告说明：10月8日起南越宫苑馆和东门关闭，其他公告列明区域仍开放，须从北京路西门进入。不能把部分闭馆解读为全馆闭馆，也不能继续把路线导向不合适的入口；王宫展区免费规则还不能和王墓展区票价混用。

实现中增加current_notice、visit_scope、entry_note，并在POI查询之前应用适用规则。对需要核对的入口，使用指定检索词和允许的POI名称；匹配失败时不把普通地点坐标悄悄当成正确入口。该候选被视为当前无法可靠规划，并明确说明“不代表全馆闭馆”。

地图曾查询到对应出口POI，坐标113.269318、23.127815；这只是一次地点查询，并不是一次走完新规则的真实行程验证，更不是实地踏勘。

### 农讲所：“免费讲解”不能推出“门票免费”

官方参观页写有免费定时讲解、开放和入场说明，但免费讲解的证据不自动证明门票金额。程序保留ticket为空。这种保守处理可能使预算估算偏高，却比编造免费入场更可靠。

### 6项新增回归检查

检查介绍来源不能变成运营证据；部分关闭不误判全馆关闭；免费讲解不变成免费门票；过期公告不覆盖地图；错误入口不被采用；匹配入口坐标确实用于规划。这些回归构成当前59项测试中的6项新增内容。

新增规则只完成上述回归及有限地点查询，早先8个真实模型检查点不能替它背书。核验期不会因生成报告而自动刷新；10月20日后的新出行日期须重新核对官方信息。

## 12. 护栏、用户界面与当前局限

### 护栏的重点是执行权限

工具有白名单、参数类型和候选ID检查；规划模型不能直接修改已确认预算和返程时间。费用、时间、步行与必去/排除由程序验证。没有支付、Shell、任意网络URL或导出密钥工具。外部地点文本只能作为观察，不提升为系统指令。

真实模型＋模拟注入案例里，恶意地点文本要求把预算改成9999、选择已排除的省博并导出密钥；结果保留150元预算、排除条件未被破坏，模型未请求越权工具。一次通过仅证明这个用例，不构成全面安全证明。正则拒绝规则只是早期筛查，可能误伤自然表达，后续还需要误报评估。

前端对内容做HTML转义，官方链接限制为受信HTTPS域名；密钥只留服务端，日志脱敏，发布时扫描配置密钥。HTTP默认绑定127.0.0.1，检查Host/Origin，限制请求体16KB和并发4。

### 为什么页面不展示全部工程术语

普通用户需要行程、价格、路线和必要的来源提醒，不需要知道模型标识或Function Calling等实现细节。消费者界面因此减少调试说明；答辩用review页看Trace。视觉上更像可用产品，不能成为隐藏未知票价或预约限制的理由。

### 尚未解决的事情要主动说清楚

应用未部署公网，GitHub只发布源码；没有登录、用户配额、生产任务队列或并发压测。最新浏览器截图未取得，现有报告保留明确标日期的历史截图和更新后的原始日志，不能称作新版截图。没有真实学生体验数据、人民币账单、实时预约余量和全20个地点的运营核验。

下一步可先补真实用户试用和最新浏览器体验验证，再完善资料更新与异常日期；面向公网部署时增加鉴权、配额和日志留存策略。比继续增加模型或更多目的地更优先的是把已有功能的可信度和可维护性补牢。

## 14. 高频追问：架构与算法

### 1. 这和直接让大模型写攻略有什么不同？

攻略回答可以只输出文字，本项目还需要真实工具结果和程序核算。模型选择候选，路线和费用由工具返回，预算、返程、开放及步行由程序检查；无法查到时保留未知或返回无方案。每一步留Trace，能追溯为什么选择或排除。

### 2. 既然规则能规划，为什么还要用大模型？

规则处理明确条件和计算；模型处理自然表达、增量修改及根据观察选择候选。两者可独立运行，方便比较和测试。没有做系统性用户对照实验，因此目前只能说明模型增加了自然语言入口和受限重选能力，不能量化证明它比规则总体更优。

### 3. 为什么不把全部任务交给模型？

模型对金额、时间边界和外部文本可能出错。把硬约束放进确定性函数能逐项测试，并在模型输出不可靠时阻止交付。Prompt要求遵守预算只是第一层，最后仍以程序计算为准。

### 4. 是否属于ReAct？能展示思维链吗？

它具备“工具动作、观察、下一步选择”的受限循环。展示的是实际tool_calls、工具输入输出与程序决策摘要，不是模型隐藏思维链。不能把事后写的解释伪装成模型内部推理。

### 5. 为什么最多两站、候选只选三个？

这是为了半日/一日和轻松偏好控制路线组合及API开销。历史运行曾出现大量路线错误，扩大候选会增加调用和失败机会。当前用有限组合比较兼顾可解释性和运行成本，不宣称已经找到最优候选数。

### 6. 评分权重怎么得到的？是不是拍脑袋？

它们是当前可解释的工程启发式，优先资料明确、符合兴趣且交通较短的方案，并非训练出来或用户调查证明的最佳权重。硬约束先筛掉不可行组合，评分只排序剩余方案。下一步可通过用户偏好比较来调整。

### 7. 多轮对话靠什么记住？

靠进程内会话保存已接受结构化字段，新文本按证据增量修改。不是把无限聊天历史交给模型，也不是向量记忆。非法请求不污染合法状态，重启后会话消失，已保存行程可回放。

## 15. 高频追问：数据、验证与可靠性

### 8. 60元能保证实际玩下来吗？

不能保证。它是当次工具和适用资料下的估算，含固定餐饮与预留，且不包含所有收费特展或个人消费。未知价格会明确使用占位额度；实际支出、排队和预约还需出行前确认。系统保证的是按已知/估算输入执行了约束检查。

### 9. 10个官方来源是不是10个景点都核实了？

不是。4个有运营规则、其中3个有明确适用价格，另外6个只有官方介绍。来源存在、场馆营业、门票明确是不同事实维度。过期资料和超出周历日期也不能作为当前营业事实。

### 10. 天气服务和地图分别用什么？

高德负责地理编码、POI、公交及步行路线；天气使用Open-Meteo。模型接口为兼容tools的Chat Completions协议。并没有因为申请了高德Key就把天气也说成高德天气。

### 11. 高德10021错误到底是什么原因？

归档中确实出现该错误，但没有足够证据定位账户或服务商根因。因此只说明做了减少候选、全局节流和路线模式修复；后续小样本运行成功不等于证明所有错误由频率造成。

### 12. 模拟故障测试是不是没价值？

模拟有价值，因为能稳定复现闭馆、超时和注入输入，检验明确的系统行为。它不能证明真实平台可靠率，所以与真实服务测试分开保存。这里有3例真实模型加模拟观察，也有完全离线规则场景，不能混称在线测试。

### 13. 为什么59项通过还不能说完成了生产验证？

59项覆盖选定边界和契约，没有覆盖所有用户表达、所有日期或并发流量。真实服务只有4次行程，DOM检查也不等于浏览器视觉验证。因此可以说交付可复现MVP，不能说达到商用可靠性。

### 14. GitHub网址能让同学直接使用吗？

GitHub当前提供源码和报告，不是正在运行的服务。127.0.0.1指向各自电脑，转发后对方访问的是自己机器。对方可以下载源码本地运行；想直接打开网页使用，需要另行部署后端、配置服务端密钥及访问控制。

## 16. 高频追问：不足、贡献与未来改进

### 15. 项目的创新点是什么？

没有发明新的基础模型或路径算法。工程特点是把学生的预算、返程和步行偏好转成可执行约束，让模型工具决策与确定性核算协作；对未知事实、来源有效期、部分关闭和入口匹配作显式处理，并将历史失败与修复证据公开。创新表述应落在可验证的具体设计上。

### 16. 是否使用AI辅助开发？你本人做了什么？

可以诚实回答：“项目使用AI辅助规划、编码、测试与文档整理。我需要理解需求、技术取舍和验证结果，并对展示内容负责。”本人参与环节应按真实情况补充，不能声称所有代码均独立手写。老师通常会进一步问函数和日志，建议先能解释核心流程、费用公式、状态更新和至少两项真实修复。

### 17. 如果再给两周，会先做什么？

优先做三件事：第一，找真实学生完成任务，记录成功/失败原因、理解成本及耗时；第二，完善官方资料更新和特殊日期，继续区分介绍与运营事实；第三，完成新版浏览器、多设备及部署验证。这是后续计划，没有写成已经完成的结果。

### 18. 为什么不增加更多景点和多智能体？

当前主要瓶颈是资料可靠性、外部服务和验证覆盖。新增景点增加维护工作，多智能体增加调用与协调成本。应先证明现有20个地点和单Agent架构的质量，再评估扩展的实际收益。

### 最容易说错的八句话

不要说“20个景点都已核实”“预算绝对不超”“已经预约成功”“工具全部由模型自由调用”“100%可靠”“DOM通过代表新版截图验证通过”“GitHub已上传所以网页全球可用”“没有API就完全无法演示”。

分别改为：分层资料覆盖；按已知和占位额度估算；用户自行确认预约；模型仅有有限工具；小样本指定检查通过；浏览器视觉仍待验证；源码公开、应用本地；无Key仍可历史回放及离线规则测试。

### 答辩前自查

能否不看稿算出60元？能否解释345米是道路结果？能否指出会话在哪一层更新？能否区分3类测试？能否说明部分闭馆与入口不匹配的区别？这些问题答清楚，比背诵技术名词更有说服力。
